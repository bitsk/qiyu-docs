# 仓库架构与职责


后续内核开发以 `bitsk/qiyu-kernel` 为主，改动按子系统独立提交，保留可 rebase 的下游补丁栈。用户态按独立功能划分，连同内核、调试与系统生成，共规划八个仓库：

| 仓库 | 维护内容 | 依赖与边界 |
| --- | --- | --- |
| `qiyu-kernel`（已存在） | 驱动、binding/DTS、内核配置、内核/模块/DTB 构建入口 | 以 Linux 主线为基底，按子系统维护提交 |
| `qiyu-device-service`（拟定） | 相机/IMU 采集、原始手柄传输、时间戳与共享缓冲、设备访问接口 | 统一管理硬件所有权，向跟踪与诊断提供数据 |
| `qiyu-head-tracking`（拟定） | 头显跟踪后端、QVR/CDSP 适配、头姿与质量输出 | 消费统一采集层，输出带时间和坐标定义的姿态 |
| `qiyu-controller-tracking`（拟定） | 手柄输入解码、光学/惯性跟踪、SDK/ABI helper | 消费统一采集数据和头部姿态，不依赖 VR runtime 回读头姿 |
| `qiyu-vr-runtime`（拟定） | OpenXR/OpenVR 接入、设备 provider、合成/呈现与光学适配 | 消费跟踪输出；固定 Monado/Mesa 上游来源和补丁版本 |
| `qiyu-vr-session`（拟定） | 服务编排、桌面/VR 切换、启动停止、资源清理与会话 CLI/API | 管理生命周期，提供调试控制入口 |
| `qiyu-debug`（拟定） | 调试网页、后端 API、遥测、相机/屏幕预览、硬件编码与 WebRTC | 前后端同仓，订阅各生产者的数据，控制请求走会话 API |
| `qiyu-rootfs`（拟定） | 多系统配方、软件包/系统服务、设备 overlay、固件导入清单、initramfs 与镜像封装 | 用固定提交/Release 与 SHA-256 装配所选组件 |

独立仓库以独立构建、版本和功能边界为依据，不强制每个仓库新增一个常驻进程。统一采集可以作为库嵌入唯一生产者，并通过共享缓冲/IPC 服务其他消费者。A081 头部与手柄跟踪共享四路相机输入；拆库后保持统一采集和曝光调度，保留帧身份、曝光时间、时钟域、缓冲生命周期和有效性信息。跟踪接口的 schema/客户端包由其所属功能仓库维护并单独标明版本，runtime 适配这些接口；拆分不放宽已有质量和时间门限。

### 可扩展的 rootfs

`qiyu-rootfs` 按以下三个维度装配，Debian/SteamOS 是初始配方：

```text
systems/<system>/    基础系统来源、包管理与构建/配置适配器
devices/<model>/     型号 overlay、固件清单与启动封装参数
profiles/<profile>/ 桌面、VR、调试或维护等功能与软件包选择
manifests/          每种组合的来源、版本、组件提交和产物摘要
```

系统适配器约定统一的获取/校验、准备根目录、安装软件包、应用配置和导出镜像阶段。后续增加其他系统时新增适配器和支持矩阵，复用设备 overlay、组件锁定及装配流程；目录结构和接口属于规划，不表示这些系统已构建或实机验证。功能 profile 可选择所需组件，维护系统无需强制装入整套 VR/调试服务。系统组合 manifest 记录全部选用仓库的提交/Release、接口版本、型号配置与 SHA-256，避免复制一份内核或运行时源码继续维护。

### 调试系统前后端同仓

`qiyu-debug` 规划为 `frontend/`、`backend/`、`api/` 三部分，共同维护协议、客户端和版本；原生视频 helper 及 H.264/WebRTC 构建入口归入后端。相机预览订阅采集层 tap，屏幕预览使用显示生产者或现有只读采集接口；保持硬件所有权和编码器租约管理。调试消费者不得阻塞生产者或另开竞争相机采集；跟踪和 VR 的正常工作不依赖调试网页在线。生命周期控制调用 `qiyu-vr-session`，设备状态、采集、编码、解码与浏览器呈现指标分别保留。

除 `qiyu-kernel` 外，其余仓库目前均为规划，实际整理上传时再建立。Monado、Mesa 等上游修改保留各自历史或独立补丁栈，以明确版本引用；只有出现独立维护需要时再增加相关依赖 fork。已有归档和 Release 保持原记录；已归档的温控用户态与完整启动镜像保留作追溯，后续系统侧维护归入 rootfs 项目，迁移时单独说明。
